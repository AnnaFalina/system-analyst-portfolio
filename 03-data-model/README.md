# ER-модель данных

## Контекст

Система хранит данные о клиентах, заказах, вещах, платежах, уведомлениях, доставке, проблемных актах и невостребованных заказах. 
Ниже представлен реестр ключевых сущностей, их атрибутов и то, в каких процессах эти данные участвуют.

## Реестр ключевых сущностей

| Сущность | Ключевые атрибуты | В каких процессах участвует |
| :--- | :--- | :--- |
| **Клиент** | `id_клиента`, ФИО, `номер_телефона`, `e-mail`, `адрес_доставки` | Оформление заказа, отправка уведомлений, курьерская доставка, онлайн-оплата, разрешение проблемных ситуаций. |
| **Сотрудник** | `id_сотрудника`, ФИО, должность, контактные данные | Приём и выдача заказов (приемщик), обработка (цех), доставка (курьер), разрешение проблем (менеджер). |
| **Заказ** | `номер_заказа`, `id_клиента`, `id_тарифа`, `дата_время_приема`, `пункт_приема`, `статус`, `дата_начала_обработки`, `дата_готовности`, `дата_выдачи`, `сумма_к_оплате`, `способ_получения`, `отмена_заказа` | Весь жизненный цикл заказа: от создания до выдачи или передачи на хранение. Является связующим звеном для всех остальных сущностей. |
| **Вещь** | `id_вещи`, `номер_заказа`, `описание_вещи`, `требуемая_работа`, `фото`, `описание_проблемы` | Оформление заказа (фиксация состояния при приеме), фиксация проблемных ситуаций, передача на хранение партнеру. |
| **Тариф** | `id_тарифа`, `тип` (обычный/экспресс), `коэффициент_стоимости`, `срок_обработки`, `доступность_тарифа` | Формирование стоимости и сроков заказа при оформлении, аналитика и отчетность. |
| **Платеж** | `id_платежа`, `номер_заказа`, `сумма_к_оплате`, `способ_оплаты`, `дата_время_платежа`, `статус_оплаты` | Онлайн-оплата, прием оплаты в пункте выдачи, формирование финансовой отчетности. |
| **Уведомление** | `id_уведомления`, `номер_заказа`, `id_клиента`, `способ_оповещения`, `текст_уведомления`, `дата_время_отправки`, `статус_оповещения` | Информирование клиента на всех этапах: оформление, готовность, проблема, передача на хранение. |
| **Курьерская доставка** | `id_доставки`, `id_сотрудника`, `номер_заказа`, `тип_операции`, `адрес_доставки`, `дата_и_временное_окно`, `стоимость_доставки`, `результат` | Логистика: забор вещей у клиента, доставка готового заказа. Интеграция с мобильным приложением курьера. |
| **Проблемный акт** | `id_проблемы`, `номер_заказа`, `id_сотрудника`, `описание_проблемы`, `фото`, `дата_выявления`, `предложенное_решение`, `статус_проблемы` | Обработка инцидентов (порча вещи, задержка), связь с клиентом и менеджером, расчет компенсаций. |
| **Невостребованный заказ** | `id_невостребованного_заказа`, `номер_заказа`, `тип_решения`, `дата_уведомления_о_готовности`, `дата_окончания_срока_хранения`, `дата_передачи_на_хранение`, `номер_места_хранения` | Учет заказов, которые клиент не забрал вовремя (свыше 30 дней), передача компании-партнеру. |

## Выявленные несоответствия (Data Quality)

При сопоставлении данных с правилами и логикой системы были выявлены следующие точки роста:

*   **Дублирование:** Атрибут `сумма_к_оплате` хранится и в сущности `Заказ`, и в сущности `Платёж`. 
    *   *Решение:* в `Заказ` храним итоговую сумму к оплате, а в `Платёж` — фактические транзакции (может быть несколько, например, предоплата и доплата).
*   **Дублирование:** Атрибут `адрес_доставки` есть и у `Клиента`, и в `Курьерской доставке`.
    *   *Решение:* в профиле клиента храним адрес по умолчанию, а в доставке — фактический адрес для конкретной операции (клиент может заказать доставку на другой адрес).
*   **Пробел:** Не описаны условия доступности тарифов (`доступность_тарифа`). 
    *   *Решение:* вынести бизнес-правила в отдельный справочник (например, «экспресс» недоступен для крупногабаритных вещей).
*   **Противоречие:** В правилах заложено 5 статусов заказа (принят, в обработке, готов, выдан, проблема), но уведомления клиенту отправляются только на 2 из них («готов» и «проблема»).
    *   *Решение:* добавить триггеры отправки уведомлений на статусы «Принят» и «Выдан», чтобы снизить количество звонков в пункт выдачи.
