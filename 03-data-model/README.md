# ER-модель данных

## Контекст

Система хранит заказы, вещи, платежи, уведомления, доставку, проблемные
акты и невостребованные заказы. Нужно спроектировать связи без дублирования
и потерь.

## Ключевые сущности

| Сущность | Назначение |
|----------|-----------|
| `Клиент` | ФИО, телефон, email, адрес доставки |
| `Заказ` | Номер, клиент, тариф, пункт, статус, даты, сумма |
| `Вещь` | Описание, требуемая работа, фото, проблема |
| `Платёж` | Сумма, способ, статус, дата |
| `Уведомление` | Канал, текст, статус доставки |
| `Курьерская доставка` | Адрес, окно, результат |
| `Проблемный акт` | Описание, фото, решение, статус |
| `Невостребованный заказ` | Дата готовности, срок хранения, место |
| `Тариф` | Тип, коэффициент, срок |
| `Сотрудник` | ФИО, должность |

## Выявленные несоответствия

- **Дублирование:** `сумма_к_оплате` есть и в `Заказ`, и в `Платёж` → хранить в `Заказ`, в `Платёж` — факт оплаты.
- **Дублирование:** `адрес_доставки` в `Клиент` и `Курьерская доставка` → адрес по умолчанию в `Клиент`, фактический — в доставке.
- **Пробел:** `Тариф / условия_доступности` не описаны → нужно бизнес-правило.
- **Противоречие:** статусов 5, а уведомления только на 2 (`готов`, `проблема`) → клиент не видит `принят`/`в_обработке`/`выдан`.
